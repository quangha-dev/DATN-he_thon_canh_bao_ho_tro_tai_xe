# Runbook chuyển SafeFleet từ MySQL sang PostgreSQL

## Nguyên tắc

- Không sửa trực tiếp các migration MySQL V1–V13 đã chạy.
- Dựng PostgreSQL song song, nạp và đối soát trước khi chuyển `DB_URL`.
- MySQL giữ nguyên ở chế độ chỉ đọc trong cửa sổ rollback.
- File lớn được chuyển sang MinIO trước khi xóa BLOB khỏi database.
- Không chạy hai backend cùng ghi vào hai database nếu chưa có cơ chế dual-write/outbox được kiểm thử.

## Pha 0 — Chuẩn bị và chốt phạm vi

1. Đóng băng thay đổi schema MySQL trong thời gian migration.
2. Ghi lại version ứng dụng, checksum Flyway, số dòng và dung lượng từng bảng.
3. Backup vật lý/logical MySQL và thử restore vào một instance độc lập.
4. Xác minh MinIO versioning/backup cho bucket tài liệu và bằng chứng.
5. Chốt quy ước thời gian nguồn: mọi `DATETIME(6)` MySQL hiện được hiểu theo `Asia/Ho_Chi_Minh`.

Không được cutover nếu backup chưa được restore thử.

## Pha 1 — Dựng PostgreSQL đích

Yêu cầu image PostgreSQL 16+ chứa:

- `pgcrypto`, `pg_trgm`;
- `vector` (pgvector);
- `postgis`.

Chạy lần lượt:

1. `V1__postgresql_baseline.sql`
2. `V2__rag_and_agent.sql`
3. `V3__postgis.sql`

Tạo ít nhất ba role:

- `safefleet_migrator`: DDL/Flyway, không dùng khi chạy ứng dụng.
- `safefleet_app`: CRUD trong schema `safefleet`, không có quyền tạo extension/schema.
- `safefleet_readonly`: báo cáo/đối soát.

Thiết lập `search_path=safefleet,public`, TLS, backup WAL và giới hạn connection. Dùng PgBouncer khi tổng connection của backend + worker có nguy cơ vượt ngân sách kết nối.

## Pha 2 — Sửa ứng dụng để tương thích PostgreSQL

Hoàn thành checklist trong `MYSQL_TO_POSTGRES_COMPATIBILITY.md`. Tối thiểu:

- JDBC driver, dialect, URL và healthcheck PostgreSQL;
- native query JSON và upsert;
- mapping `jsonb`;
- OCR upload vào MinIO, không ghi byte[] vào `document_ocr_jobs`;
- thay current driver/current vehicle bằng bảng assignment;
- tách `ocr_status` và `record_status` trong service/mobile contract;
- integration test chạy trên PostgreSQL thật bằng Testcontainers.

Trước cutover, build backend mới phải chạy được với PostgreSQL trống và toàn bộ migration mới.

## Pha 3 — Extract, transform, load thử

### Thứ tự nạp dữ liệu

1. `permissions`, `roles`, `role_permissions`, `users`.
2. `drivers`, `vehicles`, `devices`.
3. `driver_vehicle_assignments`, `vehicle_device_assignments` được suy ra từ các cột current của MySQL.
4. `object_assets` và upload file sang MinIO.
5. `trips`, timeline, session/checklist/work log.
6. mobile devices/token/sync/idempotency.
7. telemetry, safety, incident, flood, navigation.
8. notification/push.
9. warehouse documents/items/confirmation/audit.
10. OCR jobs.
11. agent command/settings/audit.
12. RAG/agent trace mới bắt đầu rỗng, trừ khi có nguồn nhập riêng.

### Quy tắc chuyển kiểu

| MySQL | PostgreSQL | Quy tắc |
|---|---|---|
| `BIGINT AUTO_INCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | Nạp ID cũ, sau đó reset sequence |
| `TINYINT(1)` | `boolean` | Chỉ nhận 0/1 |
| `DATETIME(6)` | `timestamptz(6)` | `source_value AT TIME ZONE 'Asia/Ho_Chi_Minh'` |
| `JSON` | `jsonb` | Parse bắt buộc; bản ghi JSON lỗi đưa vào quarantine |
| `LONGTEXT/MEDIUMTEXT` | `text` | UTF-8 |
| `DOUBLE` | `double precision` | Validate tọa độ/confidence |
| `DECIMAL(p,s)` | `numeric(p,s)` | Không qua float trung gian |
| `MEDIUMBLOB image_data` | MinIO + `object_assets` | SHA-256 trước/sau upload phải giống nhau |

### Chuyển tài xế–xe và thiết bị–xe

- Với mỗi cặp `drivers.current_vehicle_id`, tạo một assignment đang hoạt động.
- Đối chiếu với `vehicles.current_driver_id`. Nếu hai chiều không khớp, không tự chọn; ghi vào bảng/file quarantine để quản trị xác nhận.
- Tạo device assignment từ `vehicles.gps_device_id`, `vehicles.camera_device_id` và kiểm tra lại `devices.vehicle_id` theo cùng nguyên tắc.

### Chuyển OCR

1. Với mỗi `document_ocr_jobs.image_data` khác null, tính SHA-256 và upload MinIO bằng object key bất biến, ví dụ `ocr/{owner_id}/{job_id}/{sha256}`.
2. Tạo `object_assets`, gắn `source_asset_id` vào job.
3. Map status cũ sang `ocr_status`; tạo `record_status` độc lập dựa trên trường bắt buộc còn thiếu.
4. Các giá trị người dùng đã nhập phải vào `manual_fields`; kết quả engine vào `ocr_fields`.
5. Không để thao tác nạp/migration kích hoạt lại worker OCR.

## Pha 4 — Đối soát

### Kiểm tra bắt buộc

- Row count từng bảng nguồn/đích sau khi trừ bản ghi quarantine.
- `min(id)`, `max(id)`, count distinct ID.
- Count theo status và theo ngày/tháng cho `trips`, `safety_events`, `incidents`, `document_ocr_jobs`.
- Tổng số lượng/chi phí bằng `numeric`, không đối soát qua float.
- Không có foreign key mồ côi.
- JSON parse thành công 100% hoặc có danh sách quarantine được duyệt.
- Số object MinIO, tổng byte và SHA-256 khớp `object_assets`.
- Tọa độ nằm trong miền hợp lệ.
- Assignment hiện hành không trùng tài xế/xe/thiết bị.

Ví dụ truy vấn PostgreSQL:

```sql
SET search_path TO safefleet, public;

SELECT 'users' AS table_name, count(*) FROM users
UNION ALL SELECT 'drivers', count(*) FROM drivers
UNION ALL SELECT 'vehicles', count(*) FROM vehicles
UNION ALL SELECT 'trips', count(*) FROM trips;

SELECT driver_id, count(*)
FROM driver_vehicle_assignments
WHERE ended_at IS NULL
GROUP BY driver_id
HAVING count(*) > 1;

SELECT o.id
FROM document_ocr_jobs o
LEFT JOIN object_assets a ON a.id = o.source_asset_id
WHERE a.id IS NULL;
```

Sau khi nạp ID thủ công, reset mọi identity sequence bằng `setval(pg_get_serial_sequence(...), max(id), true)` hoặc script tự động duyệt cột identity.

## Pha 5 — Cutover

Với quy mô hiện tại, ưu tiên cutover có maintenance ngắn thay vì dual-write phức tạp:

1. Bật maintenance/read-only trên web và chặn command ghi mới từ mobile; mobile tiếp tục giữ queue offline.
2. Chờ worker OCR/push/sync đang chạy hoàn tất hoặc checkpoint an toàn.
3. Chạy delta ETL từ watermark cuối.
4. Chạy bộ đối soát nhanh và smoke test đăng nhập, danh sách chuyến, start/pause/end trip, telemetry, OCR, notification, agent.
5. Đổi secret/`DB_URL`, triển khai backend PostgreSQL.
6. Mở ghi; mobile đẩy queue bằng idempotency key hiện có.
7. Theo dõi error rate, latency, connection, lock, replication/backup trong ít nhất 24–72 giờ.

Nếu bắt buộc zero-downtime, dùng CDC (ví dụ Debezium) từ MySQL sang staging topic/table rồi áp dụng idempotent vào PostgreSQL. Không tự viết dual-write không có outbox vì có thể tạo trạng thái lệch vĩnh viễn.

## Pha 6 — Rollback

Trong cửa sổ rollback, MySQL không nhận ghi mới nên không thể chỉ đổi URL ngược lại nếu PostgreSQL đã phát sinh dữ liệu. Có hai lựa chọn:

- Rollback sớm trước khi mở ghi PostgreSQL: đổi backend về MySQL.
- Rollback sau khi đã mở ghi: đóng ghi, reverse ETL phần delta PostgreSQL về MySQL, đối soát, rồi mới đổi backend.

Không xóa volume MySQL trong tối thiểu một chu kỳ backup đầy đủ và thời gian nghiệm thu đã thống nhất. Sau đó export archive cuối, mã hóa và ghi rõ thời hạn giữ.

## Tiêu chí hoàn tất

- 100% bảng nghiệp vụ được map hoặc có quyết định loại bỏ được phê duyệt.
- Không còn BLOB OCR trong PostgreSQL.
- Sai lệch count/checksum bằng 0 hoặc nằm trong quarantine có biên bản.
- Test backend/mobile/web/agent chạy trên PostgreSQL.
- Restore backup PostgreSQL và MinIO đã được diễn tập.
- MySQL chỉ được decommission sau khi hết cửa sổ rollback.
